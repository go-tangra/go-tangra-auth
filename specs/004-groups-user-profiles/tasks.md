# Tasks: User Groups & User Profiles

**Input**: Design documents from `/specs/004-groups-user-profiles/`

**Prerequisites**: plan.md, spec.md, research.md, data-model.md, contracts/, quickstart.md

**Tests**: Tests are MANDATORY (Constitution Principle IV, NON-NEGOTIABLE). Every user story lists its tests before its implementation tasks; tests are written and confirmed failing first. Groups touch authorization, avatars touch parsing of untrusted bytes, profiles touch PII: negative security tests and fuzz targets are included.

**Organization**: Tasks are grouped by user story so each story is an independently testable increment.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: Can run in parallel (different files, no dependencies)
- **[Story]**: US1 groups grant access · US2 own profile · US3 admin edits profiles · US4 invite into groups
- Paths are repository-relative; the auth service lives in `services/auth/`, the gateway and shell in `services/gateway/`

## Path Conventions

- Go domain packages under `services/auth/internal/<pkg>` with `<pkg>db/db.go` adapters, HTTP handlers in `services/auth/internal/httpapi`, gRPC in `services/auth/internal/grpcapi`, SQL in `services/auth/internal/store`, migrations in `services/auth/internal/store/migrations`
- Console remote under `services/auth/console/src` (Vitest in `console/tests/unit`, Playwright in `console/tests/e2e`)
- Gateway identity in `services/gateway/internal/identity`, dispatcher in `services/gateway/internal/httpapi`, shell in `services/gateway/shell/src`

## Dependencies & Execution Order

- **Phase 1 → Phase 2 → stories**: contracts and schema first; every story needs `EffectiveRoleSlugs`, the session refresh and the audit vocabulary.
- **US1 (groups)** depends only on Phase 2. **US2 (own profile)** depends only on Phase 2; it can run in parallel with US1 (different packages: `authz/groups*` vs `user/profile*`, `httpapi/groups.go` vs `httpapi/profile.go`).
- **US3** depends on US2 (reuses `user.Profile`, `user.Avatar`, `AvatarEditor`). **US4** depends on US1 (`authz.Groups.AddMembers`) and US2 (profile names).
- Within a story: tests → domain service → handlers → wiring → console → Playwright.

```
Setup (T001–T006)
  └─ Foundational (T007–T018)
       ├─ US1 groups (T019–T030) ──┐
       ├─ US2 profile (T031–T047) ─┼─ US3 admin profile (T048–T053)
       │                           └─ US4 invitations (T054–T060)
       └─ Polish (T061–T066) after all stories
```

## Parallel Execution Examples

- **Setup**: T002, T003, T004, T005, T006 in parallel after T001.
- **Foundational tests**: T007–T011 together; then T012 → T013 → T014 → T015; T016, T017 alongside T014; T018 after T015.
- **US1**: T019–T023 together; T024 → T025 → T026 → T027; T028 alongside T026; T029 after T028; T030 last.
- **US2**: T031–T039 together; T040 and T041 in parallel, then T042; T043, T044, T045, T046 in parallel after T042; T047 last.
- **US1 ∥ US2**: two engineers (or agents) can run Phases 3 and 4 concurrently; the only shared files are `app.go` and `server.go` registrations (sequence those).

## Implementation Strategy

- **MVP = Phase 1 + Phase 2 + US1**: groups granting access through the existing decision path is the highest-value slice and is demonstrable in the shell (Hello nav appears when joining a group).
- **Increment 2 = US2**: profile and avatar with the gateway/shell header; independently demonstrable.
- **Increment 3 = US3 + US4**: admin conveniences on top.
- Keep the FGA model change (T003) and migration (T012) backward compatible; both are additive and were verified by T062 before release.
