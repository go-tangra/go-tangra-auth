# Auth service security model

This document describes how the tenant authentication service protects sign-in,
sessions, tokens and the authorization-code flow. It complements the Freya
framework model (`docs/security-model.md` at the repository root), which covers
the service-to-service channel the auth service itself runs on.

## Sign-in (User Story 1)

1. The console posts `tenant` (slug), `email` and `password` to `POST /api/v1/signin`
   through the edge listener (TLS 1.3, security headers, CSRF double submit for
   state-changing calls, per-IP token buckets, body limits).
2. `internal/user` resolves the tenant and account, then **always** performs one
   argon2id verification — against the stored hash or a fixed dummy hash when the
   account does not exist or has no password — and pads the whole call to a fixed
   floor (`password.PadDuration`). Unknown tenant, unknown email, wrong password,
   suspended tenant, deactivated or invited user all answer `401 {"reason":
   "invalid_credentials"}` with no cookie and the same timing (SC-006).
3. Counters live in Valkey: per-origin (`rl:signin_ip:<hash>`, 60 / 10 min) and
   per-account (`rl:signin_acct:<tenant>:<hash>`, 20 / 10 min) windows answer `429`;
   failures against a known account (`rl:fail:<user>`) reaching the tenant's
   `lockout_threshold` set `lock:<user>` for `lockout_duration` and answer `423`.
   Only lockout and rate limiting are distinguishable from a wrong password.
4. Every attempt writes a `signin_attempts` row (hashed email and IP, no
   plaintext) and an application audit event (`signin_ok`, `signin_failed`,
   `lockout`) with the closed vocabulary from `data-model.md`.
5. When the account has TOTP enabled, step one returns `{"mfa_required": true,
   "challenge": "<opaque>"}`; the challenge is stored hashed in Valkey for five
   minutes and consumed exactly once by `POST /api/v1/signin/mfa`. MFA failures
   count towards the same lockout.

## Sessions

- A session is a 256-bit random secret in the `__Host-session` cookie (`Secure;
  HttpOnly; SameSite=Strict; Path=/`). The database stores only its SHA-256.
- `internal/session` resolves the cookie through a Valkey projection
  (`sess:<hash>`, TTL = idle timeout) with a database fallback, enforces the
  tenant's absolute lifetime and idle timeout, and touches `last_seen_at` at most
  once a minute.
- Revocation fans out three ways at once: the `sessions` row, a `revocations`
  hypertable entry (the feed, 60-minute retention) and a Valkey mark
  (`rev:sid:*`, `rev:user:*`, `rev:tenant:*`) published on `auth:revoked`.
  User- and tenant-wide marks apply to sessions created before the mark.
- `GET /api/v1/sessions` lists a user's live sessions; `POST
  /api/v1/sessions/{id}/revoke` and `POST /api/v1/signout` end them.

## Proof of identity (tokens)

- `POST /api/v1/session/token` mints an EdDSA (Ed25519) JWT from a live session:
  `iss`, `sub` (user id), `tid`, `sid`, `roles`, `amr`, `iat/nbf/exp` (≤ 15 min),
  `jti` and optionally `aud` (OAuth client). No e-mail or names.
- Keys are generated by the service, sealed with the KEK envelope and stored in
  `signing_keys`. The ring rotates every 24 h (`active → retiring` after the
  rotation interval, `retiring → retired` after 30 min, removed only after
  `access_lifetime + clock_skew` since retirement). `/.well-known/jwks.json` and
  `auth.v1.Keys/List` publish every key that can still verify a token, with its
  state.
- Verification (`pkg/authclient`, used by downstream services): `alg` pinned to
  EdDSA before any signature check, `kid` must be in the current key set (an
  unknown `kid` triggers at most one refresh per minute), issuer must match,
  times are checked with ≤ 60 s skew, `exp − iat ≤ 15 min`, required claims must
  be present. The revocation feed (`Sessions/RevokedSince` or `Watch`) is polled
  every 5 s; an entry for the session, user or tenant with `ts ≥ iat` rejects the
  token, and a verifier that could not sync for longer than 60 min **fails
  closed**.
- `Sessions/Exchange` and `Sessions/MintToken` mint platform access tokens for a
  browser session on behalf of the application gateway; the policy restricts
  them to the gateway identity and every call is audited as `token_exchanged`.
- `Sessions/Introspect` exists for callers that cannot verify offline; every call
  is audited with the calling service as actor.

## OAuth 2.1 code flow

`GET /authorize` accepts only `response_type=code` with PKCE `S256`, a registered
`client_id`, an exactly matching `redirect_uri` and a `state`. Invalid requests
never redirect. A signed-out browser is bounced to the console sign-in and back.
Codes are 256-bit random values stored hashed in Valkey for 60 s, bound to the
client, redirect URI, challenge and session, and consumed on first use — a failed
exchange burns the code. Confidential clients must present their secret (argon2id
hash at rest). The resulting token carries `aud=<client_id>`.

## Groups (feature 004)

- A tenant's groups are flat. Membership is one OpenFGA tuple
  (`user:U member group:T/<gid>`); a role granted to a group is one tuple
  (`group:T/<gid>#member assignee role:T/<slug>`), so every existing
  `Check`/`BatchCheck` sees group-derived access through the model with no
  special code path, and a role change on a group of thousands is one write.
- A user's **effective roles** are the union of direct bindings and group roles
  (`store.EffectiveRoleSlugs`). Sessions, tokens (`Sessions/Exchange`,
  `MintToken`, `/api/v1/session/token`) and the admin listing use effective
  roles; cached session views record the tenant policy version and reload on
  drift, so a group change reaches an existing session on its next request
  (no re-sign-in). Tokens already issued keep their roles until expiry; every
  consulting service asks the auth service for decisions, so access itself is
  withdrawn on the next check.
- Group management (`groups:manage`) is a tenant administrator action policed
  by the same escalation guard as direct assignment: a non-owner cannot grant,
  through a group, a permission they do not hold, nor add members to a group
  carrying `admin`; `owner` is never assignable through a group (the last-owner
  rule needs direct bindings). Deleting a group requires the current member
  count. Every group, membership and group-role change is audited.

## Profiles and avatars (feature 004)

- First name, last name, phone and avatar live on the user. The phone number is
  PII: it is returned only by the owner's and administrators' profile
  endpoints, never by `/api/v1/session`, `SessionIdentity`, tokens, the profile
  lookup, audit events (which carry field names only) or logs (the framework
  redacts keys containing `phone`).
- Avatars are validated by content (sniff, header dimension gate before any
  decode, decode with the PNG/JPEG/WebP decoders only, re-encode to a 512×512
  JPEG with no metadata), stored by content hash and served only to signed-in
  members of the same tenant under `/api/v1/users/{id}/avatar/{hash}` with a
  fixed `image/jpeg` type, `nosniff`, a sandboxed CSP and private immutable
  caching. Everything else (other tenants, stale hashes, anonymous callers) is
  a uniform `not_found`.
- The upload route carries its own body limit (`x-freya-max-body-bytes`,
  2 MiB + slack, declared in the OpenAPI document); every JSON route keeps the
  64 KiB cap. Decodes are bounded by a per-instance semaphore
  (`profile.avatar_decode_concurrency`).
- A person's own profile/avatar change answers with
  `X-Freya-Identity-Refresh: 1`; the gateway drops its cached identity for
  that cookie so the platform shell shows the change on the next page load.
  Administrators' edits of other people reach the platform within the
  gateway's identity cache window (60 s).

## What the service never does

- Store or log passwords, session secrets, challenge ids, codes or tokens in
  plaintext (the Freya redacting log handler is a second line of defence).
- Answer differently for existing and non-existing accounts (except lockout and
  rate limiting, which are documented above).
- Issue a token without a live session, or accept a token signed with any
  algorithm other than EdDSA.

## Threat model (STRIDE)

| Threat | Mitigation | Verified by |
|--------|------------|-------------|
| **S** credential stuffing / brute force | argon2id, per-account + per-IP rate limits, tenant lockout threshold, TOTP | `TestLockoutAndRateLimits`, `TestSigninMatrix` |
| **S** account enumeration | identical responses + padded timing for sign-in, recovery and invitations | `TestEnumerationTiming` (SC-006), `TestCreateResendAccept` |
| **S** token forgery / alg confusion | EdDSA only, `kid` bound to published keys, `iss/aud/exp/nbf` enforced in `pkg/authclient` | `TestVerifyRefusesAlgConfusionAndForeignKeys`, `FuzzTokenParse` |
| **T** cross-tenant access via ids | tenant guard on every handler, RLS policies, tenant-prefixed FGA objects, operator grants | `TestCrossTenantMatrix` (SC-002), `TestChecksWritesAndTenantGuard` |
| **T** CSRF / XSS on the console | double-submit CSRF + Origin checks at the edge, strict CSP with nonces, HttpOnly cookies, no inline scripts | `transport/edge` tests, `TestHardening`, Playwright axe checks |
| **R** administrative actions | application audit hypertable with actor/subject/tenant/origin and a closed vocabulary | `TestAdminFlows`, `TestAdminOperations` |
| **I** secrets in logs, database or mail | Freya redaction, envelope encryption for TOTP seeds, signing keys and outbox payloads; hashes only for passwords, recovery codes, invitation/recovery tokens and session secrets | `TestRedactionScan`, `redaction-scan.sh` |
| **D** login floods | edge token buckets (per IP and per route), Freya body/header limits, Valkey counters | `TestHardening`, `TestLockoutAndRateLimits` |
| **E** self-escalation / last-owner removal | actors grant only permissions they hold; owner invariant checked before writes | `TestAssignRoles`, `TestRolesCRUDAndDecisions`, `TestSelfEscalation` |
| **E** operator abuse | platform tenant with mandatory TOTP; time-limited (≤ 4 h), reasoned, audited grants for in-tenant actions | `TestOperatorGrants`, `TestOperatorPolicyAndClients` |
| **S/T** replay after revocation | revocation marks + feed; verifiers reject within ≤ 10 s and fail closed when stale | `TestRevocationPropagation` (SC-003), `TestRevocationFeedAndFailClosed` |
| **I** key compromise | 24 h rotation, KEK outside the database, retire/republish schedule | `TestKeyRotation` (SC-007), `TestRotationStatesAndJWKS` |

## Contracts

- Browser API: `api/openapi/console.yaml` (validated at runtime; every route
  is mounted from the document and the contract test refuses drift).
- Service API: `api/proto/auth/v1/auth.proto` (`Keys`, `Sessions`,
  `Authorization`) over the Freya channel, policed by `deploy/policy.yaml`.
- Token, session and revocation semantics:
  `specs/002-tenant-auth-service/contracts/token.md`.
